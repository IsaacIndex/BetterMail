# BetterMail TechDocs

## Thread, Group, and Mailbox Semantics

The selection bar separates conversation structure from organization. **Join Thread** (`link`) creates or extends a persisted `ManualThreadGroup`; **Remove from Thread** removes only manual membership. **Create Group** (`folder.badge.plus`) immediately creates a persisted BetterMail `ThreadFolder` from one or more selected effective threads. **Move** (`folder`) is the only action that performs an Apple Mail message move. The persistence type remains `ThreadFolder`, but UI copy reserves **Group** for that BetterMail topic container and **Mailbox Folder** for an Apple Mail location. A Group may separately receive a Mailbox Folder destination; creation itself neither writes to Mail nor opens the destination sheet.

`ThreadSummaryContextBuilder` is the shared projection for interactive summary refresh and batch Re-GenAI. It orders every effective thread chronologically and gives each node its one-based position, total membership, immediate previous/next messages, and an automatic-reply or manual-thread-link relationship for each adjacency. Group membership is intentionally absent from this projection: separate threads in one `ThreadFolder` never become summary neighbours.

Node fingerprints use `node-summary-context-v2` plus the provider, full effective-thread revision, node position, adjacent message identities/content, and relationship kinds. The summary prompt is content-first: it describes the current email's information, request, decision, answer, confirmation, or action, while neighbours clarify references and what changed without lending their content to the current email. Cached summaries from older prompt versions remain readable; a changed effective-thread revision, missing cache entry, explicit regeneration, or changed message schedules the whole effective thread. `ThreadSummaryRebuildCoordinator` coalesces rethreads by generation, generates without blocking the main actor, stages every result, and commits one complete thread batch through `MessageStore.upsertSummaries`. Cancellation, supersession, or any generation failure leaves the previous batch intact. The activity center reports progress while those previous summaries remain visible.

After a successful node batch, `ThreadCanvasViewModel` publishes the complete node state, including a generation identity derived from the cache timestamp—causing Graph title fingerprints to invalidate even when regenerated text is identical—then refreshes each containing Group and ancestor Group once. Join Thread and Remove from Thread rebuild every resulting affected thread; Create Group refreshes only Group summaries. If Apple Intelligence is unavailable, threading and Group persistence still complete. `SummaryRegenerationService` hydrates every effective thread, uses the shared context and title-input builders, and atomically stages an email summary plus semantic title for each requested-range message; out-of-range messages provide context but are not written. An explicit Summaries & Titles run fails before its first write if either provider is unavailable. Once any node batch commits, a deferred completion notification makes the active thread view model republish the newly cached generations on either success or later batch/Group failure; successful runs also refresh touched Groups and ancestors first.

## Graph View

The Graph view is an opt-in sibling to the existing timeline canvas. `ThreadListView` owns the mode switch, keeps Timeline as the default, and mounts `GraphCanvasView` only when `GraphCanvasSettings.mode == .graph`.

`GraphCanvasViewModel` reuses the already-built `ThreadNode` roots from `ThreadCanvasViewModel`; it does not re-run JWZ threading. `GraphData` converts those roots into namespaced graph node IDs (`thread:<rawThreadID>`, `message:<rawMessageID>`) while retaining raw message IDs for AppleScript move operations. The thread node is also the root email's visual node; only replies become `GraphMessage` nodes. This keeps the visible email-node count equal to the visible email count. It also consumes Timeline's existing summary states plus the persisted `ThreadFolder` collection and membership map.

Collapsed history is expanded before that projection. At the raw-source decode boundary, `CollapsedEmailHistoryParser` extracts nested `message/rfc822` parts and strong forwarded/quoted header blocks, including English and common Traditional/Simplified Chinese Outlook labels. It requires a contiguous From + Date/Sent + Subject block that does not cross a blank body boundary, or an `On … wrote:` marker followed by quoted content, so ordinary prose fails closed. Each extracted email is persisted as optional JSON metadata inside its real Apple Mail parent, receives a deterministic account-and-parent-scoped logical ID, and becomes a chronological `ThreadNode` child during JWZ materialization. A matching separately fetched RFC Message-ID in the same account suppresses the logical duplicate. Logical nodes carry `EmailMessageSource` provenance: inspector content and graph titles use the extracted email, while Open in Mail, Action Item, Move, and Snip resolve or deduplicate against the containing physical message in the same account. Existing cached records acquire this metadata when their raw source is fetched again; no synthetic row participates in source reconciliation.

Outside the renderer, `GraphCanvasViewModel` projects every complete effective source thread through `ThreadSummaryContextBuilder`, even when replies are paged out, then requests titles only for visible nodes with completed summaries. `GraphTitleRequest` therefore carries the current message's content summary, chronological position and total, immediate previous/next messages, automatic-reply/manual-thread-link provenance, and the effective-thread revision. `GraphTitlePromptBuilder` tells the model to express what the current message introduces, requests, answers, clarifies, confirms, decides, follows up, or supersedes without attributing neighbour content. `GraphTitleFormatter` strips response decoration and legacy ordinal prefixes, rejects generic placement-only output, and enforces the five-word, 32-character display ceiling while preserving a trailing identifier when possible. Position influences the semantic phrase but is never displayed numerically.

Automatic title refresh, explicit **Regenerate message title**, and date-range **Regenerate Summaries & Titles** all use `GraphTitleGenerationInputBuilder`. The `graph-title-v5` fingerprint includes the prompt/provider version, effective-thread revision, summary-generation identity, position, neighbours, relationship kinds, subject, and completed summary; a hidden reply, edit, manual merge, split, or identical-text regeneration therefore invalidates an affected title. While a content summary is rebuilding, no replacement title request starts and the old label remains visible. Legacy `position/total` and ordinal prefixes are stripped before any cached title is displayed. Interactive generation publishes only after cache persistence succeeds. Batch Re-GenAI generates titles even when Graph is unmounted and writes each requested-range summary/title pair atomically; cancellation or either generation failure preserves the previous pair. All scoped-summary fetch/compare/save transactions run through one private serial Core Data context, where an older `generatedAt` result cannot overwrite a newer result even when callers overlap. Group membership is excluded, so Create Group never injects sibling-thread content into an individual title. Titles are persisted under the `graph-title` summary-cache scope. A transient model-not-ready state is retried every 30 seconds for up to ten minutes while Graph remains mounted, and Graph -> Timeline teardown cancels both readiness polling and in-flight generation. The full content summary remains in the existing summary state for reply hover and inspector detail.

Suggested Groups have a separate on-device `GraphTopicProviding` boundary and `graph-topic` summary-cache scope. One request represents one whole conversation: its root subject, the latest available thread summary, and bounded representative content sampled across the conversation. The result is either no signal or one normalized topic, display title, confidence, and user-facing supporting reason. `EmailTagProvider` remains unchanged for Timeline's three quick-scanning tags, but those per-message tags are no longer suggestion evidence.

`GraphTopicRanker` is pure and deterministic. It rejects generic workflow labels (including Update, Review, Meeting, Status, Request, and Follow up), requires at least two distinct conversations, minimum average confidence `0.68`, minimum specificity `0.52`, and minimum combined quality `0.62`, then returns at most three candidates. Combined quality is `35% specificity + 35% confidence + 15% recency/cohesion + 15% useful ungrouped membership`; none of the latter signals can rescue a candidate that misses a hard threshold. Candidates already wholly contained by one folder are skipped, equivalent normalized topics merge, duplicate member sets collapse, and stable tie-breakers make ordering repeatable. Returning zero suggestions is expected when nothing passes.

Confirmed Groups become solid intermediate `folder:<folderID>` nodes. Threads in those Groups route `You -> Group -> thread`; ungrouped threads route directly from `You`. `GraphData` builds metadata for every non-archived root, derives logical primary branches after confirmed grouping, and orders both those branches and their children by first appearance in the mailbox root order. One confirmed Group and one ungrouped thread each consume one `You` slot, regardless of the Group's member count. Passing topic candidates become dashed `suggestion:<normalizedTopic>` ghost nodes and never mutate thread identity or Group membership. Ranking runs over every non-archived root before primary paging; `GraphGrouping.reviewMembers` retains every proposed member with its full title and current Group disclosure.

Selecting a suggestion presents `Potential topic: '<title>' · <count> related threads`, its supporting reason, and **Review & Edit**, **Not this group**, and **Hide this topic**. Review & Edit is a native SwiftUI sheet with an editable name and checkbox for every proposed member. Creation requires a trimmed non-empty name and at least two selected threads, then passes exactly that name and member set through `ThreadCanvasViewModel.confirmGraphFolderSuggestion`. If any selected members already belong to Groups, `graphFolderSuggestionImpact` lists the affected Groups and whether they may be removed when emptied; a second explicit confirmation is required before persistence. Cancel leaves all membership unchanged.

The two feedback modes are independent local preferences in `GraphCanvasSettings`. **Not this group** persists the exact normalized topic plus normalized member set, so a genuinely changed membership can appear later. **Hide this topic** persists the normalized topic and suppresses it across member changes. Graph Settings reports both counts and resets both stores together. UI copy explicitly describes this as local suggestion filtering and never as model retraining.

Graph fan-out and linear email chains are paged independently. `GraphCanvasSettings.visibleBranchCount` persists **Visible branches from You** from 4 through 24 (default 10), `visibleBranchesPerNode` persists the child soft limit from 2 through 12 (default 6), and `visibleEmailsPerThread` persists **Visible emails per thread** from 2 through 50 (default 10). The email limit includes the root and controls the first page plus every later batch. `GraphRemainingBranch` uses a typed branch-or-message scope, a stable scope-derived ID, and a separate layout anchor. Message remainders render as `N emails remaining` after the last visible email and activate by pointer or VoiceOver. Per-thread expansion survives metadata refreshes, resets when the setting or mailbox scope changes, and never truncates `GraphThread`'s complete visible-message IDs used by thread actions.

Suggested Topics are outside the root quota. Each suggestion initially previews at most six members, even when they are outside the current primary page, and owns its own remainder. Projection materializes the union of threads admitted by visible primary branches and suggestion previews; a thread present through both paths is one graph node with both edges retained. This keeps ghost evidence useful while confirmed grouping exposes more unhandled mail. The controls header reports only visible/total primary branches directly under `You`, excluding ghost suggestions and synthetic remainder nodes.

### Refresh-owned semantic organization automation

`ThreadCanvasViewModel` invokes `GraphAutomationCoordinator` after every successful full rethread, so automation does not depend on the Graph view lifetime or renderer paging. The coordinator consumes complete effective roots and the same cached whole-conversation topic signals used by Graph. On first run it records an evaluated-source fingerprint baseline without proposing changes; later refreshes evaluate only new or changed sources. **Scan Current Mail** explicitly bypasses that incremental filter for the current account/mailbox scope. Cancellation and provider unavailability publish state without applying heuristic mutations.

`GraphRelationshipProviding` is injectable and returns `sameConversation`, `sameTopic`, or `unrelated` with confidence, shared anchors, named-topic/action gates, and a user-facing reason. The macOS 26 Foundation Models implementation uses a typed `@Generable` result boundary; its text parser is retained only for older compatibility. Folder profiles combine the confirmed `ThreadFolder` title with consensus signals from its members. A deterministic subject/summary shortlist excludes repeated sender/content formatting before any model call and caps each source at three Group profiles and four thread candidates. Candidate score is `0.60 relationship confidence + 0.25 shared-anchor overlap + 0.15 subject/action similarity`. Conservative attachment/folder/review thresholds are `0.94/0.90/0.78` with a `0.10` winner margin; Balanced uses `0.90/0.85/0.70` and `0.08`; Aggressive uses `0.85/0.80/0.62` and `0.05`. Attachment also requires a shared named topic plus the same concrete action/event. Automatic processing orders same-conversation components before Group assignment and prefers an existing target in the winning Group, then an existing manual group, then the oldest stable source. A single loose email is one source; a multi-message JWZ branch is indivisible.

`GraphAutomationProposal` persists its ordered attach, append, and optional Mailbox Folder steps, evidence, execution/Mail state, exact mutation delta, and deterministic identity derived from provider version plus source/action/target fingerprints. `GraphAutomationObservationEntity` records evaluated-source fingerprints. Evidence changes supersede stale proposals, while rejection suppresses only the exact unchanged relationship. Pending, failed, and recovery rows are retained until resolved; terminal applied/rejected/undone history is pruned after 30 days and capped at 500 entries.

`MessageStore.applyGraphAutomationBatch` uses one serialized organization-write context. Preflight rechecks current fingerprints and accounts, partitions stale/conflicting rows back to review, deduplicates overlaps, executes attachments before folder appends, and commits valid membership and automation deltas in one Core Data save followed by one rethread. It preserves a destination Group's ID, title, color, hierarchy, and mailbox mapping, remaps Group membership to the resulting manual-group ID, prevents duplicate membership, and leaves an emptied source Group intact. Automatic application never merges two existing manual groups, crosses accounts for attachment, moves an existing thread out of another confirmed Group, or creates a new Group. The existing mailbox-rule store is UserDefaults-backed rather than Core Data-backed, so its deterministic identity remap is serialized immediately after the Core Data commit and is idempotent on refresh.

If the destination Group maps to an Apple Mailbox Folder, automation moves only newly attached/appended physical messages through the exact-ID Mail boundary and records each original account/mailbox path. Unmapped Groups never move Mail. A committed app grouping is not rolled back by a later Mail failure. Partial Mail success compensates only reported moved IDs back to their exact origins; complete compensation returns the row to retryable failure, while incomplete compensation becomes **Recovery Needed** and never auto-loops. Ordinary failures use refresh-driven 1-, 5-, and 30-minute backoff before requiring manual retry. Undo removes only the recorded membership delta, preserves later unrelated edits, and restores exact recorded Mail routes; stale app state or incomplete restoration stays visible as Retry Undo/Recovery rather than overwriting newer work.

The persistent **Automation** toolbar control and `Shift-Command-U` app command present a destination-grouped sheet with Pending, Applied, Failed, and Recovery sections. Rows expose complete-source inclusion, destination editing, confidence/evidence, message counts, expected Mail effect, approve/reject, destination-level Approve All, retry, and undo. Settings persist the master pause, per-action Off/Review/Automatic mode, per-action Conservative/Balanced/Aggressive preset, Mailbox Folder-follow toggle, full-scope scan, and history/baseline reset. Pausing cancels active semantic evaluation, and scanning is disabled until automation resumes. `GraphData` projects pending attach/append rows as dashed links anchored to the existing solid destination. When a confirmed destination exists, `GraphTopicRanker` suppresses the corresponding duplicate ghost Group hub.

`GraphRepresentable` is the renderer adapter. It mounts `ObsidianGraphScene`, which consumes `GraphData` and emits the same selection, scope-aware expansion, hover, water, prune, folder-drop, viewport, and position callbacks used by the rest of BetterMail. Both the active scene/simulator and compiled legacy scene/simulator render, position, hover, and expand multiple remainder nodes; expansion callbacks carry a typed branch or message scope, while message layout uses the last visible email as a distinct anchor. `GraphData` also carries JWZ/manual provenance: only rendered message-to-message adjacencies crossing a manual boundary become `.manualChain`, rendered in accessible red with a `[4,4]` dash. Natural reply edges and the synthetic thread-to-first-message edge remain `.chain`. Both kinds share physics, hit testing, selection, Snip, filtering, and hover behavior. This keeps graph identity and user actions in `GraphCanvasViewModel`; the scene owns only drawing, camera input, hit testing, and physics. A folder drop resolves the dragged graph thread or reply back to its raw thread ID and the solid grouping node to its persisted `ThreadFolder` ID, then `GraphCanvasView` delegates the mutation to `ThreadCanvasViewModel.moveThread`; suggested-topic nodes are excluded. On removal the adapter pauses the `SKView`, asks the scene to clear callbacks/actions/data, and detaches it before Timeline layout begins. `ThreadListView` disables the crossfade specifically when leaving Graph so both heavy renderers are not active in one transition. The previous `GraphScene` / `GraphForceSimulator` implementation remains compiled for historical regression tests but is no longer mounted by the app.

`ObsidianGraphForceSimulator` uses deterministic seeded initial positions plus Center, Repel, Link, and Link-distance forces. The roomier defaults raise repulsion from the original 2,400 to 5,200 and link distance from 92 to 140. The concise-label release runs a one-time migration that floors older compact Repel and Link distance values at those defaults while preserving custom Center, Link strength, and Damping values; subsequent user edits are not remigrated. The pairwise cutoff and minimum clearance are also wider. Confirmed Group membership is copied onto every node in that Group corpus; pairs crossing from a Group corpus to a different or ungrouped corpus receive stronger repulsion over a wider range. A date-normalized chronology rank derived from `GraphThread.lastUpdated` adds both an initial radial offset and a gentle ongoing radial preference, making newer threads settle closer to `You` even when input order differs. The `You` node initializes at the scene center but remains freely draggable and unpins on release like every other node. Existing positions, including a moved `You` position, survive data rebuilds, and scene resizes translate them by the center delta. Integration is frame-normalized, finite-checked, damped, and bounded by an energy/frame settle gate. Active rendering prefers 60 FPS and settled rendering 12 FPS. Reduce Motion runs extra integration work per frame, applies stronger damping, and ends the settle window earlier.

`ObsidianGraphSceneNode` renders a small circle, focus ring, and plain text label rather than a botanical card. Email nodes prefer the cached Apple Intelligence graph title, then fall back to the subject and sender while a title is pending. The full content summary stays separate for inspector display and search and is never substituted as a node title. Labels remain single-line and width-capped as a final safety net; the scene does not relocate or suppress labels at runtime. The shorter titles and roomier force layout are the overlap controls. Hit testing remains geometric against the scaled circular mark, not SpriteKit child bounds, so label text cannot select or drag a node. Suggested groups and the remaining-page hub use dashed rings. Edges are trimmed to node radii and rendered as straight `SKShapeNode` paths; suggestion/remaining edges are dashed and arrows are optional. At hover or selection, direct neighbors and their links are emphasized while unrelated nodes dim. Search results use the same dimming path. Label alpha is derived from zoom plus the persisted Text fade threshold, with the focused node and direct neighbors always visible.

Dragging is single-node, matching Obsidian: the grabbed node is pinned to the pointer with its original grab offset, while linked neighbors continue reacting through the force solver. Descendants are not rigidly translated. When the grabbed node is a thread or reply, eligible solid confirmed-folder destinations are temporarily pinned so repulsion cannot move them away. Each destination uses a 44-point zoom-aware magnetic release target and highlights when the pointer enters it; release persists the whole thread in that folder before the graph projection refreshes. Releasing elsewhere unpins both the grabbed node and temporary destinations, then wakes a bounded settle. Blank drag, right drag, trackpad scrolling, pinch, command/control-scroll, and empty-canvas double-click retain the existing unbounded camera behavior. Hover is cleared at the start of a drag, pan, or zoom and returns only after a later pointer movement.

`ThreadListView` owns one persistent search field in the shared top bar across Default, Timeline, and Graph. Default and Timeline filter the root projection recursively so a matching reply retains its whole thread; Graph consumes the same query to highlight direct matches while preserving related nodes as context. `ObsidianGraphControls` remains a SwiftUI overlay with Obsidian's Filters, Groups, Display, and Forces sections, but no longer duplicates search. Filters contains both persisted branch page sizes, with localized labels and explanatory help. Graph Settings exposes the same steppers. Groups reports confirmed and suggested graph groups without mutating them. Display persists Arrows, Text fade threshold, Node size, and Link thickness. Forces persists Center, Repel, Link, and Link distance; Restore resets both force and display values. The separate Graph Settings sheet includes the local suggestion-preference reset. Legacy radial/ribbon settings remain readable for backward compatibility but are not used by the mounted renderer.

The May and July 2026 Instruments/drag results describe the retired radial/ribbon runtime and are historical only. They are not current acceptance evidence. Current verification is the `ObsidianGraphForceSimulatorTests` suite, a normal app build with the full log captured in `/tmp/xcodebuild.log`, and an installed-app interaction check.

The graph palette now routes through `DesignTokens.Graph.AppTheme`, which maps the canvas to the app's light/dark appearance instead of the retired v1 palette. SpriteKit nodes and SwiftUI chrome use the same AppTheme ink, panel, accent, snip, archive, live, and water tokens.

Viewport state is centralized through `GraphViewport` and shared by the SwiftUI toolbar and SpriteKit scene. The SpriteKit scene uses viewport-sized rendering over unbounded world coordinates: force integration and branch placement are not clamped to the scene frame, camera pan has no positional boundary, and resize preserves the current pan offset while recentering the root coordinate system. The graph supports `20%...500%` zoom, multiplicative toolbar zoom, pinch-to-zoom through `GraphSKView`, command/control-scroll zoom around the cursor, native two-finger trackpad pan without modifier keys, blank-canvas drag pan, right-drag pan, and double-click empty-canvas recenter.

`ThreadListView` passes graph-specific chrome insets into `GraphCanvasView`: a trailing reservation for the inspector and a bottom reservation for the selected-message action bar. The SpriteKit canvas and SwiftUI graph toolbar therefore render in the remaining visible lane instead of under app chrome.

Pruning has two independent paths. Archive retains its existing app-only contract and persists `ArchivedInGraphEntry` rows through `MessageStore`. Normal sidebar scopes exclude those archived threads across Default, Timeline, and Graph views; the `Graph Archive` sidebar item shows only the archived set until an explicit Restore History action removes the archive row.

Snip is modeled separately as `GraphSnipPhase.idle`, `.staging`, `.allocating`, and `.moving`. Entering staging ignores the current graph selection. `ObsidianGraphScene` resolves a thread node, reply node, or either owning edge to one whole-thread target; a solid confirmed-folder node or its `You -> folder` trunk resolves to a confirmed-group target. Suggested-topic nodes/edges, `You`, and remainder nodes return no Snip target. `GraphCanvasViewModel` snapshots group members from the complete current `ThreadNode` source rather than the paged renderer projection, then deduplicates items by graph thread ID. The first staged item locks a normalized Mail account; mixed-account groups cannot establish the lock, and after locking they stage only matching descendants. Removing the final item clears it.

Staging never mutates graph geometry. The scene runs a quick cut/return effect on visible thread edges and nodes, followed by persistent dimmed Snip styling; confirmed groups reflect partial/full staging. Group transitions cascade only across visible descendants with a bounded delay. Reduce Motion replaces the cut effect with a crossfade. The fixed toolbar slot reads **Snip** with zero items and **Allocate (N)** otherwise. The staging capsule exposes a pointer-accessible **Cancel Snipping**, and Canvas Escape clears the full session. Archive is disabled while staged/allocating/moving, while camera, zoom, recenter, and settings remain available. Leaving Graph or changing source scope discards the ephemeral session without touching Mail.

`SnipMoveSheet` presents a fixed, case-insensitively matched Mail account and the complete searchable hierarchy of its existing folders. There is no default destination. A bulk picker changes only its own draft until **Apply to all** is invoked; every `GraphSnipItem`, including paged-out group members, then retains an independent override. **Move All** requires every row to reference a current folder. Sheet dismissal, Escape, and **Back to Graph** preserve staged styling plus `GraphSnipAllocation` drafts; **Discard Snips & Exit** clears both. Dismissal is disabled only while `.moving`, when the frozen request and progress stay visible.

Mail movement is behind the narrow `GraphSnipMailMoving` protocol. `MailAppleScriptClient.moveMessages` resolves the source mailbox/account directly, compares RFC IDs case-insensitively, attempts requested messages, and returns `GraphMailMoveResult` containing the exact normalized IDs Mail reported moved. `GraphCanvasViewModel` processes source/destination tuples serially and continues after failures. Required messages already at the destination count as satisfied. A fully satisfied item receives its own exact-location Restore History entry and joins one batch prune animation; zero moved IDs leave it unchanged. A partial move triggers compensation of only the reported IDs back from the destination to each message's original mailbox. Complete compensation classifies the item as rolled back; incomplete compensation leaves the branch visible and creates a recovery-marked history entry containing only messages still displaced. One aggregate notice reports succeeded, unchanged, rolled-back, and recovery-needed counts after every allocation is attempted.

`GraphCompostEntry.movedMessages` records message ID, source account/path, and destination account/path. Restore groups only those recorded messages by destination-to-origin tuple and updates an incomplete recovery entry to the residual displaced set. Legacy entries can still use the previous single-mailbox fallback. Successful Snip and Archive removals keep their branches rendered through the SpriteKit prune animation; `GraphCanvasViewModel` retains the existing 2.2-second id-checked fallback so a lost scene callback cannot leave a branch half-pruned.

`GraphRestoreHistoryControl` mounts **History (N)** beside Snip and Archive. Its 344-point popover is capped and scrollable, partitions newest-first entries into Snipped and Archived sections, and shows subject, timestamp, source-to-destination route, and partial-recovery warning. Opening the popover and interacting with row content are non-mutating; restoration is available only through **Restore** or **Retry Restore**. One restore can run at a time: the popover disables every row action immediately, and `GraphCanvasViewModel` independently enforces the same single-flight boundary around its shared prune state. **Dismiss** requires confirmation and calls only `GraphCanvasViewModel.dismissRestoreHistoryEntry`, which removes the row and records its internal entry ID in a session-only suppression set. It never calls `GraphSnipMailMoving` or deletes `ArchivedInGraphEntry`; therefore a dismissed persistent archive entry returns in a new app session.

A graph thread or message exposes Action Item through its native right-click context menu. The menu toggles the resolved physical email through the existing `ThreadCanvasViewModel` / `MessageStore` action-item path, whether the user right-clicks a thread node, a real message leaf, or a logical forwarded/quoted-history leaf. Action-item identity and persistence are scoped by account plus normalized RFC Message-ID; legacy accountless rows bind to the first matching physical account when next tagged, so equal IDs in IBM and iCloud do not cross-toggle or cross-delete.

The persistent Snip, Archive, and History controls keep stable toolbar footprints. Snip always enters or advances its explicit batch, while Archive still acts immediately on a selected thread or enters branch-picking mode without one; History only presents details until an explicit row action is selected. Water and other sparse-node feedback remain unchanged.

## Inspector Message Presentation

`MailAppleScriptClient` treats Apple Mail `content` as a possible MIME document rather than assuming every non-empty value is display text. `HeaderDecoder` recognizes complete MIME messages and boundary-led cached fragments, prefers inline `text/plain` across nested multipart structures, decodes transfer encodings/charsets, ignores declared attachments, and converts HTML-only block/list markup into readable plain-text spacing. Unparsed MIME framing fails closed so boundaries and part headers never become user-facing content. Paragraph breaks survive both ingestion and `SnippetFormatter`; the display-time pass also cleans previously cached malformed snippets without a data migration.

`ThreadInspectorView` renders From and To as parsed contact rows with distinct name/address typography. Quoted commas, folded headers, angle-bracket addresses, semicolon-separated lists, and RFC group prefixes stay grouped correctly. Recipient lists show four entries initially, expose the remaining count through an explicit disclosure, retain selectable text, and publish stable accessibility identifiers for From, To, and Email content.

## Exhaustive Day Fetch and Coverage

`DayFetchCoordinator` is the single actor-isolated ingestion path for app-start refresh, toolbar refresh, auto-refresh, calendar recovery, visible-range backfill, and Settings backfill. Each operation uses the current calendar and timezone to resolve `[dayStart, nextDayStart)`; open days stop at the current second. A lightweight, uncapped manifest identifies every Apple Mail message in the source interval, while payloads are fetched by `internalMailID` in configurable requests of 1–4 messages. Four is a request batch size, never a total fetch limit.

Refresh mode compares manifest metadata with both visible and source-absent cache records and downloads only new or changed lightweight payloads. Calendar and range recovery use full payloads. Payloads remain staged until a second manifest matches the first; a changed mailbox retries once. Cancellation, missing payload IDs, or a second unstable manifest records a failed attempt without committing staged payloads or changing source-absence flags.

Coverage is persisted per concrete account/mailbox/day in `DayFetchCoverageEntity`. Aggregate Inbox operations first enumerate Inbox for every Mail account, record zero-message child scopes, and derive their displayed state from the least-complete child. `MessageStore` records first touch, attempt/success timestamps, covered-through time, expected/fetched/absent counts, state, and sanitized error text. Historic cache rows and `lastSyncDate` do not imply coverage after migration.

After an authoritative manifest, `MessageStore` upserts returned mail, clears any prior source-absence state, and flags cached messages missing from that exact source interval. Normal message, thread, action-item, search, selection, and Mail-action inputs exclude flagged rows; reconciliation queries explicitly include them so a later fetch can restore them. The toolbar month grid maps unknown/fetching/partial/verified/failed to gray/blue/amber/green/red, disables future days, and always confirms a selected day before re-fetching it.

Calendar mail is classified from decoded raw MIME into invitation, attendance-only response, supplemented response, other scheduling message, ordinary message, or indeterminate. The payload `METHOD` overrides a conflicting Content-Type parameter; nested transfer encodings and folded iCalendar lines are decoded, secondary `.ics` attachments are ignored as scheduling signals, and malformed/oversized input fails open. Only attendance-only `REPLY` records are suppressed. A non-empty escaped `COMMENT` is attendee-authored supplement text and becomes the node snippet, while generated plain-text alternatives alone do not make an RSVP visible. Invitations, edited RSVP responses, and ordinary Reply All supplements remain real email nodes regardless of event date.

Suppressed RSVP records stay in Apple Mail, Core Data, reconciliation, and JWZ containers. Thread-only store reads include them and recursively resolve cached ancestors beyond the seven-day display window. Missing parents are fetched on a dedicated background Mail client in cancellable four-ID batches through exact Message-ID lookup restricted to the originating Apple Mail account, so cached threading and ordinary refresh are not queued behind a potentially slow source scan. An ordinary Reply All can probe its immediate missing parent, but unrelated recovered mail is discarded and never recursively expands; records are admitted only when the ancestry resolves to a calendar invitation/response. JWZ promotes descendants across hidden RSVP containers, yielding invitation A → supplement C from A → hidden RSVP B → C, and maps hidden B to the same structural membership without materializing or counting it. If A cannot be recovered, C remains a temporary real root. The idempotent V2 source repair waits no more than 30 seconds for foreground Mail activity, preventing repeating refresh work from starving migration. It prioritizes currently visible legacy candidates, then reclassifies every remaining RSVP candidate through its stored mailbox/internal-ID reference in batches of four and persists the optional calendar kind through lightweight Core Data migration. A stale numeric Apple Mail ID retries the RFC Message-ID in the cached concrete mailbox before an account-wide exact Message-ID scan. Accountless virtual-mailbox rows are skipped rather than causing a cross-account scan; a sole legacy accountless match may be promoted to the fetched account, while ambiguous matches remain untouched and visible. Transient failures remain eligible for a later retry.

See `docs/DataFlow.md`, `docs/Architecture.md`, and the canonical `openspec/specs/backfill` and `openspec/specs/auto-refresh` specifications for the detailed contracts.

## Processing Activity Center

`ProcessingActivityCenter` is the shared observable model for app-wide loading and processing state. Long-running operations register an activity when they begin, update optional detail/progress while they run, and finish with completed, failed, or cancelled state. This keeps user-visible work such as latest-mail refreshes, mailbox hierarchy loading, visible-range backfill, batch import, Apple Intelligence summaries/tags, and Re-GenAI in one activity timeline instead of scattered loading indicators.

`BetterMailApp` owns a single activity center and passes it into `ContentView`, `ThreadCanvasViewModel`, and `AutoRefreshSettingsView`. The center is visible in two places:

- a `MenuBarExtra` for system-level visibility while the main window is covered or inactive
- a passive `ProcessingActivityShelf` toast over the main app content for a fresh activity start or finish

Operation-specific views may still keep action buttons disabled or show detailed settings text, but the canonical visual status for active processing is the activity center.

### Fixed Main-Window Activity Toast

The menu bar remains the durable activity timeline. `ProcessingActivityShelf` is a non-interactive, one-line, 224-point-wide status toast intended only as a short update reminder. It shows for four seconds after activity start or finish, then disappears without removing the retained activity record.

`ContentView` mounts the toast directly on the root `NavigationSplitView`, with a fixed bottom-right position. It intentionally does not react to graph toolbar, inspector, or potential-topic overlays:

- trailing inset: `18`
- bottom inset: `18`

The toast does not accept pointer interaction, so it cannot block controls beneath it. Full activity history, details, and active counts remain available through the `MenuBarExtra`.
