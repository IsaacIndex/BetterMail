# BetterMail TechDocs

## Graph View

The Graph view is an opt-in sibling to the existing timeline canvas. `ThreadListView` owns the mode switch, keeps Timeline as the default, and mounts `GraphCanvasView` only when `GraphCanvasSettings.mode == .graph`.

`GraphCanvasViewModel` reuses the already-built `ThreadNode` roots from `ThreadCanvasViewModel`; it does not re-run JWZ threading. `GraphData` converts those roots into namespaced graph node IDs (`thread:<rawThreadID>`, `message:<rawMessageID>`) while retaining raw message IDs for AppleScript move operations. The thread node is also the root email's visual node; only replies become `GraphMessage` nodes. This keeps the visible email-node count equal to the visible email count. It also consumes Timeline's existing summary states plus the persisted `ThreadFolder` collection and membership map. Outside the renderer, the view model asks Apple Intelligence to compress each visible email's subject and completed summary into a 2–5 word graph title; subject text alone never starts title generation. `GraphTitleFormatter` removes response decoration and enforces a five-word, 32-character ceiling while preserving a trailing identifier when possible. Titles are fingerprinted and persisted under the `graph-title` summary-cache scope. A transient model-not-ready state is retried every 30 seconds for up to ten minutes while Graph remains mounted, and Graph -> Timeline teardown cancels both readiness polling and in-flight generation. The full summary remains in the existing summary state for reply hover and inspector detail.

Suggested folders have a separate on-device `GraphTopicProviding` boundary and `graph-topic` summary-cache scope. One request represents one whole conversation: its root subject, the latest available thread summary, and bounded representative content sampled across the conversation. The result is either no signal or one normalized topic, display title, confidence, and user-facing supporting reason. `EmailTagProvider` remains unchanged for Timeline's three quick-scanning tags, but those per-message tags are no longer suggestion evidence.

`GraphTopicRanker` is pure and deterministic. It rejects generic workflow labels (including Update, Review, Meeting, Status, Request, and Follow up), requires at least two distinct conversations, minimum average confidence `0.68`, minimum specificity `0.52`, and minimum combined quality `0.62`, then returns at most three candidates. Combined quality is `35% specificity + 35% confidence + 15% recency/cohesion + 15% useful ungrouped membership`; none of the latter signals can rescue a candidate that misses a hard threshold. Candidates already wholly contained by one folder are skipped, equivalent normalized topics merge, duplicate member sets collapse, and stable tie-breakers make ordering repeatable. Returning zero suggestions is expected when nothing passes.

Confirmed folders become solid intermediate `folder:<folderID>` nodes. Threads in those folders route `You -> folder -> thread`; ungrouped threads route directly from `You`. `GraphData` builds metadata for every non-archived root, derives logical primary branches after confirmed grouping, and orders both those branches and their children by first appearance in the mailbox root order. One confirmed folder and one ungrouped thread each consume one `You` slot, regardless of the folder's member count. Passing topic candidates become dashed `suggestion:<normalizedTopic>` ghost nodes and never mutate thread identity or folder membership. Ranking runs over every non-archived root before primary paging; `GraphGrouping.reviewMembers` retains every proposed member with its full title and current folder disclosure.

Selecting a suggestion presents `Potential topic: '<title>' · <count> related threads`, its supporting reason, and **Review & Edit**, **Not this group**, and **Hide this topic**. Review & Edit is a native SwiftUI sheet with an editable name and checkbox for every proposed member. Creation requires a trimmed non-empty name and at least two selected threads, then passes exactly that name and member set through `ThreadCanvasViewModel.confirmGraphFolderSuggestion`. If any selected members already belong to folders, `graphFolderSuggestionImpact` lists the affected folders and whether they may be removed when emptied; a second explicit confirmation is required before persistence. Cancel leaves all membership unchanged.

The two feedback modes are independent local preferences in `GraphCanvasSettings`. **Not this group** persists the exact normalized topic plus normalized member set, so a genuinely changed membership can appear later. **Hide this topic** persists the normalized topic and suppresses it across member changes. Graph Settings reports both counts and resets both stores together. UI copy explicitly describes this as local suggestion filtering and never as model retraining.

Graph fan-out is paged at two independent levels; topic ranking and the linear reply-chain cap are not. `GraphCanvasSettings.visibleBranchCount` persists **Visible branches from You** from 4 through 24 (default 10). `visibleBranchesPerNode` persists the child soft limit from 2 through 12 (default 6). Each parent with hidden children receives a `GraphRemainingBranch` containing a stable ID, `parentID`, hidden count, and next-page count. The root retains `remaining:threads`; child IDs are derived from their owning parent. Clicking a remainder increments only that parent's limit. Changing the root setting resets root pagination, changing the per-node setting resets child pagination, and ordinary title/tag refreshes retain both. Each admitted thread still renders its first 10 emails as one root/thread node plus at most nine reply nodes, while `GraphThread` keeps the complete message count and raw message IDs for snip/archive actions.

Suggested Topics are outside the root quota. Each suggestion initially previews at most six members, even when they are outside the current primary page, and owns its own remainder. Projection materializes the union of threads admitted by visible primary branches and suggestion previews; a thread present through both paths is one graph node with both edges retained. This keeps ghost evidence useful while confirmed grouping exposes more unhandled mail. The controls header reports only visible/total primary branches directly under `You`, excluding ghost suggestions and synthetic remainder nodes.

`GraphRepresentable` is the renderer adapter. It mounts `ObsidianGraphScene`, which consumes `GraphData` and emits the same selection, parent-scoped expansion, hover, water, prune, folder-drop, viewport, and position callbacks used by the rest of BetterMail. Both the active scene/simulator and compiled legacy scene/simulator render, position, hover, and expand multiple remainder nodes; expansion callbacks carry the owning `parentID`. This keeps graph identity and user actions in `GraphCanvasViewModel`; the scene owns only drawing, camera input, hit testing, and physics. A folder drop resolves the dragged graph thread or reply back to its raw thread ID and the solid grouping node to its persisted `ThreadFolder` ID, then `GraphCanvasView` delegates the mutation to `ThreadCanvasViewModel.moveThread`; suggested-topic nodes are excluded. On removal the adapter pauses the `SKView`, asks the scene to clear callbacks/actions/data, and detaches it before Timeline layout begins. `ThreadListView` disables the crossfade specifically when leaving Graph so both heavy renderers are not active in one transition. The previous `GraphScene` / `GraphForceSimulator` implementation remains compiled for historical regression tests but is no longer mounted by the app.

`ObsidianGraphForceSimulator` uses deterministic seeded initial positions plus Center, Repel, Link, and Link-distance forces. The roomier defaults raise repulsion from the original 2,400 to 5,200 and link distance from 92 to 140. The concise-label release runs a one-time migration that floors older compact Repel and Link distance values at those defaults while preserving custom Center, Link strength, and Damping values; subsequent user edits are not remigrated. The pairwise cutoff and minimum clearance are also wider. Confirmed folder membership is copied onto every node in that folder corpus; pairs crossing from a folder corpus to a different or ungrouped corpus receive stronger repulsion over a wider range. A date-normalized chronology rank derived from `GraphThread.lastUpdated` adds both an initial radial offset and a gentle ongoing radial preference, making newer threads settle farther from `You` even when input order differs. The `You` node initializes at the scene center but remains freely draggable and unpins on release like every other node. Existing positions, including a moved `You` position, survive data rebuilds, and scene resizes translate them by the center delta. Integration is frame-normalized, finite-checked, damped, and bounded by an energy/frame settle gate. Active rendering prefers 60 FPS and settled rendering 12 FPS. Reduce Motion runs extra integration work per frame, applies stronger damping, and ends the settle window earlier.

`ObsidianGraphSceneNode` renders a small circle, focus ring, and plain text label rather than a botanical card. Email nodes prefer the cached Apple Intelligence graph title, fall back to the existing full summary while a title is pending, and finally fall back to the subject before a summary is ready. Labels remain single-line and width-capped as a final safety net; the scene does not relocate or suppress labels at runtime. The shorter titles and roomier force layout are the overlap controls. Hit testing remains geometric against the scaled circular mark, not SpriteKit child bounds, so label text cannot select or drag a node. Suggested groups and the remaining-page hub use dashed rings. Edges are trimmed to node radii and rendered as straight `SKShapeNode` paths; suggestion/remaining edges are dashed and arrows are optional. At hover or selection, direct neighbors and their links are emphasized while unrelated nodes dim. Search results use the same dimming path. Label alpha is derived from zoom plus the persisted Text fade threshold, with the focused node and direct neighbors always visible.

Dragging is single-node, matching Obsidian: the grabbed node is pinned to the pointer with its original grab offset, while linked neighbors continue reacting through the force solver. Descendants are not rigidly translated. When the grabbed node is a thread or reply, eligible solid confirmed-folder destinations are temporarily pinned so repulsion cannot move them away. Each destination uses a 44-point zoom-aware magnetic release target and highlights when the pointer enters it; release persists the whole thread in that folder before the graph projection refreshes. Releasing elsewhere unpins both the grabbed node and temporary destinations, then wakes a bounded settle. Blank drag, right drag, trackpad scrolling, pinch, command/control-scroll, and empty-canvas double-click retain the existing unbounded camera behavior. Hover is cleared at the start of a drag, pan, or zoom and returns only after a later pointer movement.

`ObsidianGraphControls` is a SwiftUI overlay with Obsidian's Filters, Groups, Display, and Forces sections. Filters binds to BetterMail's existing graph search plus both persisted branch page sizes, with localized labels and explanatory help. Graph Settings exposes the same steppers. Groups reports confirmed and suggested graph groups without mutating them. Display persists Arrows, Text fade threshold, Node size, and Link thickness. Forces persists Center, Repel, Link, and Link distance; Restore resets both force and display values. The separate Graph Settings sheet includes the local suggestion-preference reset. Legacy radial/ribbon settings remain readable for backward compatibility but are not used by the mounted renderer.

The May and July 2026 Instruments/drag results describe the retired radial/ribbon runtime and are historical only. They are not current acceptance evidence. Current verification is the `ObsidianGraphForceSimulatorTests` suite, a normal app build with the full log captured in `/tmp/xcodebuild.log`, and an installed-app interaction check.

The graph palette now routes through `DesignTokens.Graph.AppTheme`, which maps the canvas to the app's light/dark appearance instead of the retired v1 palette. SpriteKit nodes and SwiftUI chrome use the same AppTheme ink, panel, accent, snip, archive, live, and water tokens.

Viewport state is centralized through `GraphViewport` and shared by the SwiftUI toolbar and SpriteKit scene. The SpriteKit scene uses viewport-sized rendering over unbounded world coordinates: force integration and branch placement are not clamped to the scene frame, camera pan has no positional boundary, and resize preserves the current pan offset while recentering the root coordinate system. The graph supports `20%...500%` zoom, multiplicative toolbar zoom, pinch-to-zoom through `GraphSKView`, command/control-scroll zoom around the cursor, native two-finger trackpad pan without modifier keys, blank-canvas drag pan, right-drag pan, and double-click empty-canvas recenter.

`ThreadListView` passes graph-specific chrome insets into `GraphCanvasView`: a trailing reservation for the inspector and a bottom reservation for the selected-message action bar. The SpriteKit canvas and SwiftUI graph toolbar therefore render in the remaining visible lane instead of under app chrome.

Pruning has two independent paths. Archive retains its existing app-only contract and persists `ArchivedInGraphEntry` rows through `MessageStore`. Normal sidebar scopes exclude those archived threads across Default, Timeline, and Graph views; the `Graph Archive` sidebar item shows only the archived set until a Compost restore removes the archive row.

Snip is modeled separately as `GraphSnipPhase.idle`, `.staging`, `.allocating`, and `.moving`. Entering staging ignores the current graph selection. `ObsidianGraphScene` resolves a thread node, reply node, or either owning edge to one whole-thread target; a solid confirmed-folder node or its `You -> folder` trunk resolves to a confirmed-group target. Suggested-topic nodes/edges, `You`, and remainder nodes return no Snip target. `GraphCanvasViewModel` snapshots group members from the complete current `ThreadNode` source rather than the paged renderer projection, then deduplicates items by graph thread ID. The first staged item locks a normalized Mail account; mixed-account groups cannot establish the lock, and after locking they stage only matching descendants. Removing the final item clears it.

Staging never mutates graph geometry. The scene runs a quick cut/return effect on visible thread edges and nodes, followed by persistent dimmed Snip styling; confirmed groups reflect partial/full staging. Group transitions cascade only across visible descendants with a bounded delay. Reduce Motion replaces the cut effect with a crossfade. The fixed toolbar slot reads **Snip** with zero items and **Allocate (N)** otherwise. The staging capsule exposes a pointer-accessible **Cancel Snipping**, and Canvas Escape clears the full session. Archive is disabled while staged/allocating/moving, while camera, zoom, recenter, and settings remain available. Leaving Graph or changing source scope discards the ephemeral session without touching Mail.

`SnipMoveSheet` presents a fixed, case-insensitively matched Mail account and the complete searchable hierarchy of its existing folders. There is no default destination. A bulk picker changes only its own draft until **Apply to all** is invoked; every `GraphSnipItem`, including paged-out group members, then retains an independent override. **Move All** requires every row to reference a current folder. Sheet dismissal, Escape, and **Back to Graph** preserve staged styling plus `GraphSnipAllocation` drafts; **Discard Snips & Exit** clears both. Dismissal is disabled only while `.moving`, when the frozen request and progress stay visible.

Mail movement is behind the narrow `GraphSnipMailMoving` protocol. `MailAppleScriptClient.moveMessages` resolves the source mailbox/account directly, compares RFC IDs case-insensitively, attempts requested messages, and returns `GraphMailMoveResult` containing the exact normalized IDs Mail reported moved. `GraphCanvasViewModel` processes source/destination tuples serially and continues after failures. Required messages already at the destination count as satisfied. A fully satisfied item receives its own exact-location Compost entry and joins one batch prune animation; zero moved IDs leave it unchanged. A partial move triggers compensation of only the reported IDs back from the destination to each message's original mailbox. Complete compensation classifies the item as rolled back; incomplete compensation leaves the branch visible and creates a recovery-marked Compost entry containing only messages still displaced. One aggregate notice reports succeeded, unchanged, rolled-back, and recovery-needed counts after every allocation is attempted.

`GraphCompostEntry.movedMessages` records message ID, source account/path, and destination account/path. Restore groups only those recorded messages by destination-to-origin tuple and updates an incomplete recovery entry to the residual displaced set. Legacy entries can still use the previous single-mailbox fallback. Successful Snip and Archive removals keep their branches rendered through the SpriteKit prune animation; `GraphCanvasViewModel` retains the existing 2.2-second id-checked fallback so a lost scene callback cannot leave a branch half-pruned.

A graph thread or message exposes Action Item through its native right-click context menu. The menu toggles the resolved email through the existing `ThreadCanvasViewModel` / `MessageStore` action-item path, whether the user right-clicks a thread node or one of its message leaves.

The persistent Snip and Archive controls keep stable toolbar footprints but do not share a selection contract: Snip always enters or advances its explicit batch, while Archive still acts immediately on a selected thread or enters branch-picking mode without one. Water and other sparse-node feedback remain unchanged.

## Exhaustive Day Fetch and Coverage

`DayFetchCoordinator` is the single actor-isolated ingestion path for app-start refresh, toolbar refresh, auto-refresh, calendar recovery, visible-range backfill, and Settings backfill. Each operation uses the current calendar and timezone to resolve `[dayStart, nextDayStart)`; open days stop at the current second. A lightweight, uncapped manifest identifies every Apple Mail message in the source interval, while payloads are fetched by `internalMailID` in configurable requests of 1–4 messages. Four is a request batch size, never a total fetch limit.

Refresh mode compares manifest metadata with both visible and source-absent cache records and downloads only new or changed lightweight payloads. Calendar and range recovery use full payloads. Payloads remain staged until a second manifest matches the first; a changed mailbox retries once. Cancellation, missing payload IDs, or a second unstable manifest records a failed attempt without committing staged payloads or changing source-absence flags.

Coverage is persisted per concrete account/mailbox/day in `DayFetchCoverageEntity`. Aggregate Inbox operations first enumerate Inbox for every Mail account, record zero-message child scopes, and derive their displayed state from the least-complete child. `MessageStore` records first touch, attempt/success timestamps, covered-through time, expected/fetched/absent counts, state, and sanitized error text. Historic cache rows and `lastSyncDate` do not imply coverage after migration.

After an authoritative manifest, `MessageStore` upserts returned mail, clears any prior source-absence state, and flags cached messages missing from that exact source interval. Normal message, thread, action-item, search, selection, and Mail-action inputs exclude flagged rows; reconciliation queries explicitly include them so a later fetch can restore them. The toolbar month grid maps unknown/fetching/partial/verified/failed to gray/blue/amber/green/red, disables future days, and always confirms a selected day before re-fetching it.

See `docs/DataFlow.md`, `docs/Architecture.md`, and the canonical `openspec/specs/backfill` and `openspec/specs/auto-refresh` specifications for the detailed contracts.

## Processing Activity Center

`ProcessingActivityCenter` is the shared observable model for app-wide loading and processing state. Long-running operations register an activity when they begin, update optional detail/progress while they run, and finish with completed, failed, or cancelled state. This keeps user-visible work such as latest-mail refreshes, mailbox hierarchy loading, visible-range backfill, batch import, Apple Intelligence summaries/tags, and Re-GenAI in one activity timeline instead of scattered loading indicators.

`BetterMailApp` owns a single activity center and passes it into `ContentView`, `ThreadCanvasViewModel`, and `AutoRefreshSettingsView`. The center is visible in two places:

- a `MenuBarExtra` for system-level visibility while the main window is covered or inactive
- `ProcessingActivityShelf` over the main app content for active/recent work in the current window

Operation-specific views may still keep action buttons disabled or show detailed settings text, but the canonical visual status for active processing is the activity center.

### Shared Bottom-Right Avoidance (Graph Compost vs Activity Shelf)

To keep `ProcessingActivityShelf` from covering Graph's restore chips, `GraphCanvasView` publishes the padded Compost panel bounds through an internal anchor preference (`GraphCompostPanelAnchorPreferenceKey`) when the panel is visible. Because the anchor is attached after Compost's bottom padding, it includes the existing selection-action-bar reservation without duplicating that height in the root shell.

`ContentView` resolves that preference and computes the shelf inset from the root height and panel top:

- default inset: `18`
- compost present: `max(18, (rootHeight - compostPanel.minY) + 8)`

This dynamically handles one or multiple Compost rows, keeps a constant 8-point gap above the panel, and preserves the previous 18-point minimum when Compost is absent. Existing shelf behavior stays unchanged for z-order, popover/action behavior, transition, hit-testing, and accessibility identifiers.
