# BetterMail TechDocs

## Graph View

The Graph view is an opt-in sibling to the existing timeline canvas. `ThreadListView` owns the mode switch, keeps Timeline as the default, and mounts `GraphCanvasView` only when `GraphCanvasSettings.mode == .graph`.

`GraphCanvasViewModel` reuses the already-built `ThreadNode` roots from `ThreadCanvasViewModel`; it does not re-run JWZ threading. `GraphData` converts those roots into namespaced graph node IDs (`thread:<rawThreadID>`, `message:<rawMessageID>`) while retaining raw message IDs for AppleScript move operations. The thread node is also the root email's visual node; only replies become `GraphMessage` nodes. This keeps the visible email-node count equal to the visible email count. It also consumes Timeline's existing summary states plus the persisted `ThreadFolder` collection and membership map. Outside the renderer, the view model asks Apple Intelligence to compress each visible email's subject and completed summary into a 2–5 word graph title; subject text alone never starts title generation. `GraphTitleFormatter` removes response decoration and enforces a five-word, 32-character ceiling while preserving a trailing identifier when possible. Titles are fingerprinted and persisted under the `graph-title` summary-cache scope. A transient model-not-ready state is retried every 30 seconds for up to ten minutes while Graph remains mounted, and Graph -> Timeline teardown cancels both readiness polling and in-flight generation. The full summary remains in the existing summary state for reply hover and inspector detail.

Suggested folders have a separate on-device `GraphTopicProviding` boundary and `graph-topic` summary-cache scope. One request represents one whole conversation: its root subject, the latest available thread summary, and bounded representative content sampled across the conversation. The result is either no signal or one normalized topic, display title, confidence, and user-facing supporting reason. `EmailTagProvider` remains unchanged for Timeline's three quick-scanning tags, but those per-message tags are no longer suggestion evidence.

`GraphTopicRanker` is pure and deterministic. It rejects generic workflow labels (including Update, Review, Meeting, Status, Request, and Follow up), requires at least two distinct conversations, minimum average confidence `0.68`, minimum specificity `0.52`, and minimum combined quality `0.62`, then returns at most three candidates. Combined quality is `35% specificity + 35% confidence + 15% recency/cohesion + 15% useful ungrouped membership`; none of the latter signals can rescue a candidate that misses a hard threshold. Candidates already wholly contained by one folder are skipped, equivalent normalized topics merge, duplicate member sets collapse, and stable tie-breakers make ordering repeatable. Returning zero suggestions is expected when nothing passes.

Confirmed folders become solid intermediate `folder:<folderID>` nodes whenever at least one member is visible. Threads in those folders route `You -> folder -> thread`; ungrouped threads route directly from `You`. Passing topic candidates become dashed `suggestion:<normalizedTopic>` ghost nodes and never mutate thread identity or folder membership. Ranking runs over every non-archived root in the current Graph source scope before branch paging; only visible members receive SpriteKit edges, but `GraphGrouping.reviewMembers` retains every proposed member with its full title and current folder disclosure.

Selecting a suggestion presents `Potential topic: '<title>' · <count> related threads`, its supporting reason, and **Review & Edit**, **Not this group**, and **Hide this topic**. Review & Edit is a native SwiftUI sheet with an editable name and checkbox for every proposed member. Creation requires a trimmed non-empty name and at least two selected threads, then passes exactly that name and member set through `ThreadCanvasViewModel.confirmGraphFolderSuggestion`. If any selected members already belong to folders, `graphFolderSuggestionImpact` lists the affected folders and whether they may be removed when emptied; a second explicit confirmation is required before persistence. Cancel leaves all membership unchanged.

The two feedback modes are independent local preferences in `GraphCanvasSettings`. **Not this group** persists the exact normalized topic plus normalized member set, so a genuinely changed membership can appear later. **Hide this topic** persists the normalized topic and suppresses it across member changes. Graph Settings reports both counts and resets both stores together. UI copy explicitly describes this as local suggestion filtering and never as model retraining.

Graph rendering work is paged at the branch and email levels; topic ranking is not. `GraphCanvasSettings.visibleBranchCount` persists a user-selected page size from 4 through 24 (default 10). The first render maps only that many thread branches plus a synthetic `remaining:threads` branch; clicking that remaining node expands by the same configured count until all source roots are visible. The remaining branch uses a dedicated graph edge kind so the force layout treats it like a trunk while SpriteKit renders it as a dashed lightweight connector into a hollow expandable hub, visually separating it from real email threads. Each visible branch renders its first 10 emails as one root/thread node plus at most nine reply nodes, while `GraphThread` keeps the complete message count and raw message IDs for snip/archive actions. Hidden roots and capped replies are not converted into force-simulation bodies until their page is visible, keeping the initial SpriteKit scene bounded even when the mailbox has thousands of messages; their proposed topic membership remains visible in Review & Edit before any confirmation.

`GraphRepresentable` is the renderer adapter. It mounts `ObsidianGraphScene`, which consumes `GraphData` and emits the same selection, expansion, hover, water, prune, viewport, and position callbacks used by the rest of BetterMail. This keeps graph identity and user actions in `GraphCanvasViewModel`; the scene owns only drawing, camera input, hit testing, and physics. On removal the adapter pauses the `SKView`, asks the scene to clear callbacks/actions/data, and detaches it before Timeline layout begins. `ThreadListView` disables the crossfade specifically when leaving Graph so both heavy renderers are not active in one transition. The previous `GraphScene` / `GraphForceSimulator` implementation remains compiled for historical regression tests but is no longer mounted by the app.

`ObsidianGraphForceSimulator` uses deterministic seeded initial positions plus Center, Repel, Link, and Link-distance forces. The roomier defaults raise repulsion from the original 2,400 to 5,200 and link distance from 92 to 140. The concise-label release runs a one-time migration that floors older compact Repel and Link distance values at those defaults while preserving custom Center, Link strength, and Damping values; subsequent user edits are not remigrated. The pairwise cutoff and minimum clearance are also wider. Confirmed folder membership is copied onto every node in that folder corpus; pairs crossing from a folder corpus to a different or ungrouped corpus receive stronger repulsion over a wider range. A date-normalized chronology rank derived from `GraphThread.lastUpdated` adds both an initial radial offset and a gentle ongoing radial preference, making newer threads settle farther from `You` even when input order differs. The `You` node initializes at the scene center but remains freely draggable and unpins on release like every other node. Existing positions, including a moved `You` position, survive data rebuilds, and scene resizes translate them by the center delta. Integration is frame-normalized, finite-checked, damped, and bounded by an energy/frame settle gate. Active rendering prefers 60 FPS and settled rendering 12 FPS. Reduce Motion runs extra integration work per frame, applies stronger damping, and ends the settle window earlier.

`ObsidianGraphSceneNode` renders a small circle, focus ring, and plain text label rather than a botanical card. Email nodes prefer the cached Apple Intelligence graph title, fall back to the existing full summary while a title is pending, and finally fall back to the subject before a summary is ready. Labels remain single-line and width-capped as a final safety net; the scene does not relocate or suppress labels at runtime. The shorter titles and roomier force layout are the overlap controls. Hit testing remains geometric against the scaled circular mark, not SpriteKit child bounds, so label text cannot select or drag a node. Suggested groups and the remaining-page hub use dashed rings. Edges are trimmed to node radii and rendered as straight `SKShapeNode` paths; suggestion/remaining edges are dashed and arrows are optional. At hover or selection, direct neighbors and their links are emphasized while unrelated nodes dim. Search results use the same dimming path. Label alpha is derived from zoom plus the persisted Text fade threshold, with the focused node and direct neighbors always visible.

Dragging is single-node, matching Obsidian: the grabbed node is pinned to the pointer with its original grab offset, while linked neighbors continue reacting through the force solver. Descendants are not rigidly translated. Release unpins the node and wakes a bounded settle. Blank drag, right drag, trackpad scrolling, pinch, command/control-scroll, and empty-canvas double-click retain the existing unbounded camera behavior. Hover is cleared at the start of a drag, pan, or zoom and returns only after a later pointer movement.

`ObsidianGraphControls` is a SwiftUI overlay with Obsidian's Filters, Groups, Display, and Forces sections. Filters binds to BetterMail's existing graph search and persisted branch page size. Groups reports confirmed and suggested graph groups without mutating them. Display persists Arrows, Text fade threshold, Node size, and Link thickness. Forces persists Center, Repel, Link, and Link distance; Restore resets both force and display values. The separate Graph Settings sheet includes the local suggestion-preference reset. Legacy radial/ribbon settings remain readable for backward compatibility but are not used by the mounted renderer.

The May and July 2026 Instruments/drag results describe the retired radial/ribbon runtime and are historical only. They are not current acceptance evidence. Current verification is the `ObsidianGraphForceSimulatorTests` suite, a normal app build with the full log captured in `/tmp/xcodebuild.log`, and an installed-app interaction check.

The graph palette now routes through `DesignTokens.Graph.AppTheme`, which maps the canvas to the app's light/dark appearance instead of the retired v1 palette. SpriteKit nodes and SwiftUI chrome use the same AppTheme ink, panel, accent, snip, archive, live, and water tokens.

Viewport state is centralized through `GraphViewport` and shared by the SwiftUI toolbar and SpriteKit scene. The SpriteKit scene uses viewport-sized rendering over unbounded world coordinates: force integration and branch placement are not clamped to the scene frame, camera pan has no positional boundary, and resize preserves the current pan offset while recentering the root coordinate system. The graph supports `20%...500%` zoom, multiplicative toolbar zoom, pinch-to-zoom through `GraphSKView`, command/control-scroll zoom around the cursor, native two-finger trackpad pan without modifier keys, blank-canvas drag pan, right-drag pan, and double-click empty-canvas recenter.

`ThreadListView` passes graph-specific chrome insets into `GraphCanvasView`: a trailing reservation for the inspector and a bottom reservation for the selected-message action bar. The SpriteKit canvas and SwiftUI graph toolbar therefore render in the remaining visible lane instead of under app chrome.

Pruning has two paths:

- Snip moves all raw message IDs in the thread to a Mail mailbox via `MailAppleScriptClient.moveMessages`, scoped to the thread's known source mailbox and account. The scan stops as soon as every requested ID has moved, then adds a temporary compost chip with the previous mailbox for restore. The graph keeps the branch rendered while the SpriteKit prune animation runs and removes it only after the animation completion callback.
- Snip destination rows resolve the thread account case-insensitively. A configured default parent mailbox narrows the list only when it matches; otherwise the sheet renders the account's full mailbox tree instead of an empty picker.
- Archive is app-only and persists `ArchivedInGraphEntry` rows through `MessageStore`. Normal sidebar scopes exclude those archived threads across Default, Timeline, and Graph views; the `Graph Archive` sidebar item shows only the archived set until a compost restore removes the archive row.

Both prune actions begin a SpriteKit branch animation and normally finish through the scene callback. `GraphCanvasViewModel` also schedules a 2.2-second id-checked fallback so a scene rebuild, resize, or lost animation completion cannot leave the branch permanently half-pruned.

A graph thread or message exposes Action Item through its native right-click context menu. The menu toggles the resolved email through the existing `ThreadCanvasViewModel` / `MessageStore` action-item path, whether the user right-clicks a thread node or one of its message leaves.

The persistent Snip and Archive toolbar actions follow the same selection contract: with a selected thread they act on it immediately, and without a selection they enter branch-picking mode. Branch-picking accepts a branch line, thread node, or message node; edge tolerance stays visually consistent across zoom levels. Water and prune feedback remain available on the sparse node marks.

The Snip sheet uses native `List` selection so the highlighted mailbox is the value sent to the move operation. `MailAppleScriptClient` resolves that path within the selected account, compares RFC message IDs without case sensitivity, and requires Mail to report at least one moved message before the graph hides the thread. Restore retains the original account and mailbox path.

Focused graph coverage lives in `Tests/GraphTests.swift`. The current runtime tests verify deterministic finite initialization, centered-but-movable `You` behavior, link convergence, single-node drag isolation, position preservation across rebuilds, zoom/threshold label fading, graph-title normalization/cache reuse, summary-gated generation, cancellation when Graph disappears, roomier force defaults and migration, and the single-line label safety cap. Suggested-topic tests cover normalization, generic rejection, hard thresholds, scoring order, top-three and zero-result behavior, deduplication, branch-page stability, dedicated provider/cache reuse, exact rejection versus topic hiding, persistence/reset, and changed membership. Review view-model tests verify that edited names and selected members reach the existing confirmation path exactly and that existing-folder impact requires confirmation while cancellation remains non-mutating. Confirmed folder projection accepts one or more currently visible members, so singleton and partially paged folders retain their solid graph hub; thread IDs are trimmed before folder membership matching. Existing mapping, folder/ghost grouping, paging, viewport, triage, and prune state-machine tests remain the contract around the adapter. Legacy radial/ribbon tests remain useful only for the compiled fallback implementation and should not be interpreted as current interaction behavior.

## Processing Activity Center

`ProcessingActivityCenter` is the shared observable model for app-wide loading and processing state. Long-running operations register an activity when they begin, update optional detail/progress while they run, and finish with completed, failed, or cancelled state. This keeps user-visible work such as latest-mail refreshes, mailbox hierarchy loading, visible-range backfill, batch import, Apple Intelligence summaries/tags, and Re-GenAI in one activity timeline instead of scattered loading indicators.

`BetterMailApp` owns a single activity center and passes it into `ContentView`, `ThreadCanvasViewModel`, and `AutoRefreshSettingsView`. The center is visible in two places:

- a `MenuBarExtra` for system-level visibility while the main window is covered or inactive
- `ProcessingActivityShelf` over the main app content for active/recent work in the current window

Operation-specific views may still keep action buttons disabled or show detailed settings text, but the canonical visual status for active processing is the activity center.
